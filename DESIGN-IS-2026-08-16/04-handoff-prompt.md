Verdict paragraph (quoted from 03-verdict.md):
> MagicLens has a sound structure — a real semantic design-token system, an honest and consistently-gated confirmation UX, a fast primary resource-management workflow, and a differentiated feature set beyond its Lens-derived navigation pattern — but its execution has measurable consistency debt: the token system it built is inconsistently enforced (raw color/spacing/type values leak past it throughout the stylesheet), focus-visible styling is nearly absent, motion is never gated for reduced-motion users, the JS-heavy dependency set ships unsplit, and one concrete page-level duplication (Cluster Overview vs. Nodes) confuses which surface is authoritative for cluster health. None of this is a foundational or purpose-level failure — every finding is a "tighten what's already there" fix, not a "start over" one. That is the textbook REFINE case: the bones are good, iterate.

Fix in priority order (top moves from the audit, verbatim):
1. Principle #10/#4 — Resolve the Cluster Overview / Nodes duplication: Both pages independently call `useClusterMetrics` and render `NodesHealthBanner` plus a near-identical CPU/Memory/Pods `ResourceUsageCard` grid. Evidence: `ClusterOverviewPage.tsx:54,100-141` vs. `NodesOverviewPage.tsx:299,306` / `NodesResourceGrid.tsx:73-110`. Pick one canonical home for cluster-wide health/usage summary and have the other page link to it (or show a slimmer, distinctly-scoped summary) instead of re-rendering the same widget pair.
2. Principle #3 — Enforce the design-token system instead of leaking past it: `tokens.ts:22-30` declares a 7-step spacing scale that is never wired into any CSS custom property (dead code — never referenced by `buildTheme.ts`); 19+ ad hoc spacing values and 20 font-size values (vs. a declared 6-step type scale) are actually used across `global.css`; 220 raw hex/rgb color literals bypass the token system entirely (e.g. `global.css:194,358,393,1302-1404`). Wire the declared spacing/type tokens into actual CSS variables and sweep the stylesheet to consume them instead of one-off literals.
3. Principle #8 — Build out `:focus-visible` coverage: only 4 rules exist across a 14,027-line stylesheet (`global.css:852,3404,3611,3684`) despite dozens of distinct custom interactive-element classes (resource-kind tabs, overview stat tiles, list rows, table rows, toolbar buttons). Add a systematic focus-ring treatment keyed to the existing `--ml-primary` token, applied consistently across all custom (non-native-browser-default) interactive components. Fold in while here: expand "MFA" on first use in `en.ts` (12 occurrences, never expanded to "multi-factor authentication"); add `aria-label` to icon-only `MoreHorizontal` kebab buttons (`ResourceRowActions.tsx:148`, `WorkloadResourceRowActions.tsx:211`, `Helm/HelmRowActions.tsx:14`); add `ArrowLeft`/`ArrowRight` keyboard handling to the resource-kind tab list in `ResourceKindTabBar.tsx` to complete the ARIA `tab` pattern it already started (currently only `Enter`/`Space` activate the focused tab — no arrow-key roving).
4. Principle #9 — Respect `prefers-reduced-motion`; reduce unsplit bundle weight: zero matches for `prefers-reduced-motion` anywhere in the renderer despite 17 always-running CSS `infinite` animations (splash-drift ×5, VPN visualization pulses/shimmers, status-dot pulse, live-indicator pulse, generic shimmer/spin loaders — full list in `01-evidence.md`). Gate all of them behind a `prefers-reduced-motion: reduce` media query. Separately, `electron.vite.config.ts` has no code-splitting/manualChunks config for Monaco (74M on disk)/antd (58M)/@kubernetes/client-node (56M)/recharts/framer-motion/@xyflow, all direct dependencies with no lazy-loading evidence found — investigate route/feature-based code-splitting (e.g. Monaco only needed for the YAML editor, Sparks canvas view, and topology graph aren't needed on first paint).
5. Principle #2/#10 — Nodes dashboard: replace fixed-order sections with real flexibility (user-requested). Today `src/renderer/src/components/Nodes/NodesDashboardSettings.tsx` only supports show/hide + linear drag-reorder of fixed-height sections (health banner, resource grid, insights/top-consumers hotspots, node table, events strip — all defined in `NodesOverviewPage.tsx`). The user explicitly wants (a) more widget/metric options beyond the current 6 sections, and (b) a genuinely more flexible panel layout, not just linear reordering. Column selection for the Nodes table already exists (`TableColumnPicker` wired via `ResourceTable.tsx`'s `nodesTableContent`) — do not re-propose that part. Scope this as its own sub-plan: what new widgets make sense (candidates: per-node CPU/memory sparkline history, taint/toleration summary, kubelet version skew warning — validate against what data is already available via `useClusterMetrics`/`useNodeMetrics` before proposing new backend work), and what "more flexible layout" concretely means (resizable-width columns of sections vs. a full drag-anywhere grid — a full free-grid is a materially bigger scope than resizable columns/rows, so present both as options with effort estimates rather than assuming the bigger one).

Out of scope for this refine pass: full navigation/information-architecture redesign (the Lens-derived sidebar/tab structure scored acceptably and isn't broken); replacing antd or the existing `--ml-*` token architecture (token *enforcement* is the fix, not token *replacement*); the Sparks notes/vault feature's own UX (not audited in this pass — its performance issues were already fixed in a separate session this same day, see `ROADMAP.md` section 4); VPN feature UX (not audited in this pass).

Deliverables for the plan:
- Per-fix: target files, exact change, verification step (build on the file:line evidence above — don't re-discover it)
- Token/spec changes (move 2) consolidated in one place (ideally `buildTheme.ts` + a single audit-and-replace pass over `global.css`, not scattered edits)
- Regression checklist for both "Keep" items above
- For move 5 (Nodes dashboard flexibility): two concrete options (resizable-section-widths vs. full drag-anywhere grid) with rough effort/risk for each, since this is the one item that's a feature request rather than a consistency fix and deserves an explicit choice before implementation starts

Anti-patterns to guard against (specific to REFINE):
- Adding new abstractions where a direct change suffices (e.g. don't build a new "design system v2" — wire the existing declared tokens)
- Restyling areas that already scored 3 (the primary CRUD flow's speed, and the honest/consistent confirmation copy — don't touch either while doing the token/focus-ring/motion sweep)
- Scope creep into structural redesign (if move 1's consolidation starts to feel like it needs a new information architecture rather than picking-one-canonical-page, stop and flag it — that would no longer be a REFINE-shaped change)
- Letting the Nodes-dashboard flexibility work (move 5) balloon into a general-purpose dashboard-builder framework before validating the user actually wants that scope — present the two options and let the user pick
